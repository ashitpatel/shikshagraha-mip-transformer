# Golden Example 2 — Time-Budgeted Project Scoping MIP (revised from "Time-Knapsack")

> **Role in the eval set:** the reference case where the **participatory budgeting (PB) process** gate says **ABSTAIN**, but the **budget-capped choice technique** gate says **APPLY**. It tests whether the transformer can borrow knapsack reasoning **without** labelling the work as PB.
> Revised from the user-supplied "Time-Knapsack" outline (2026-11-04). The changes are listed at the end.

## Expected gate decisions

| Gate | Decision | Reason |
|---|---|---|
| PB process | **ABSTAIN** | No constituency allocating a shared public resource. A team of 4–5 divides its own time. That's prioritisation, not participatory budgeting. |
| Budget-capped choice technique | **APPLY** | A hard cap (team hours) and more options than fit. Knapsack reasoning helps. |
| Connected Learning | **APPLY** | Production-centred (a finished project), peer-supported (team roles), interest-powered (stretch "moonshot" features), academically oriented (graded criteria). |

**Labelling rule for the transformer:** call this a *"time-budget prioritisation routine (adapted from knapsack voting)"*. Don't call it "participatory budgeting" or "the Stanford PB phase".

## MIP metadata

| Field | Value |
|---|---|
| **MIP title** | Finishing on Time: Teaching Project Teams to Scope Within a Time Budget |
| **MIP owner** | Subject teacher running project-based learning (PBL) for one class |
| **Objective** | Project teams in Class X plan their project within a fixed time budget, finish on time, and can explain what they chose not to build and why. |
| **Domain (MI framework)** | Pedagogy |
| **Target group** | Classes 9–12 (adaptable to Classes 6–8 with smaller budgets and teacher-given estimates) |

## Teacher steps (the MIP)
1. **Before the project:** set the time budget and list the **must-have criteria** from the grading rubric.
2. **Period 1:** run student Steps 1–2 (below).
3. **Period 2:** run student Step 3 and approve each team's scope commitment.
4. **During the project:** a 5-minute check-in each week. Run the mid-point re-scope (Step 4).
5. **After submission:** a 10-minute class reflection on estimates vs. actual hours. Record the success indicators.

## Student routine

```
[1 List Features] → [2 Estimate & Assign] → [3 Prioritise Within Budget] → [4 Track & Re-scope]
```

### Step 1 — List Features
- **Action:** the team lists every feature or deliverable it would ideally build.
- **Guardrail:** must-have rubric criteria are marked **LOCKED**. Every student adds at least one item, including at least one "moonshot".
- **Artefact:** *Master Feature List*

### Step 2 — Estimate & Assign
- **Action:** for each feature, the team agrees an hours estimate **and a likely owner**.
- **Guardrail — realistic estimates:** for any task over 3 hours, the team writes down what the estimate is based on (e.g. "a 2-minute video edit took us 6 hours last time").
- **Guardrail — hours aren't interchangeable:** an estimate is tied to who can do the task. If only one student can do it, the hours count against that student's capacity.
- **Artefact:** *Time Cost Matrix* (feature · hours · owner · basis for the estimate)

### Step 3 — Prioritise Within Budget
- **Planning cap:** plan to **80% of the budget** (e.g. 16 of 20 hours). The remaining 20% is a buffer for estimation errors.
- **Order:**
  1. LOCKED features are funded first. If they alone exceed the planning cap, tell the teacher; the scope or the budget must change.
  2. For the remaining hours, each member fills a personal knapsack ballot of optional features within the remaining hours.
  3. Count the ticks per feature and fund in order while the hours last. A feature that doesn't fit is skipped.
- **Guardrail — justify the trade-off:** for each feature that's cut, the team writes one sentence: "We chose ___ over ___ because ___."
- **Guardrail — fair load:** check that no member's assigned hours exceed 1.25× an equal share, and that roles aren't split by gender stereotypes (e.g. girls always on decoration and writing).
- **Artefact:** *Scope Commitment*, signed by all members and approved by the teacher

### Step 4 — Track & Re-scope
- **Action:** each student logs hours per feature on a shared chart (paper or a spreadsheet).
- **Mid-point re-scope:** once 50% of the hours are used, compare progress with the plan. If the team is behind, drop the lowest-ranked optional feature, not the buffer or the locked items.
- **Artefact:** *Hours Tracker* (a simple burn-down chart: hours left vs. features left)

## Changes from the original outline

| Original | Revised | Why |
|---|---|---|
| "The Stanford PB Phase", "Scope Pruning Vote" | "Prioritise Within Budget", labelled as *adapted from knapsack voting* | A team dividing its own time isn't PB, which needs a constituency and a shared public resource. Avoids framework-washing. |
| Student-only routine | Teacher-owned MIP with teacher steps, plus the student routine | A MIP is a school improvement owned by a teacher or HT |
| Plan to the full 20 hours | Plan to 80% (16 hours) + a mid-point re-scope | Estimates are uncertain; knapsack assumes known costs |
| Hours treated like money | Estimates tied to owners; per-student load check | Student hours aren't interchangeable |
| Every feature voted on, foundational ones included | Rubric must-haves locked in before the vote | Stops a team voting away graded requirements |
| No equity check | Load and gender-role check | Prevents one student carrying the team or stereotyped roles |
| No duration or indicators | One project cycle; measurable success indicators | MIP template expectations |
